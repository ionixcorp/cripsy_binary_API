# Fase 0 — Inventario de contratos y matriz de compatibilidad

**Estado:** inventario completado sobre 0.3.1; ver nota de estado.
**Fecha:** 2026-11-09.
**Plan:** [`0.4.0-plan.md`](0.4.0-plan.md).
**Base:** `cripsy_binary_API` 0.3.1.

> **Nota de estado (0.3.2):** este inventario se cerró sobre 0.3.1 y conserva
> esa línea base como evidencia. La release 0.3.2 implementó
> `PayoutQuote`/`quote_payout`; el estado vigente está en el plan 0.4.0.

## 1. Alcance y método

Este documento inventaría la superficie pública afectada por 0.4.0 y clasifica
cada cambio propuesto antes de escribir código.

La compatibilidad que se evalúa es **compatibilidad de fuente** para Rust y
Python, no compatibilidad binaria/ABI. Rust no garantiza ABI estable entre
versiones y el crate está en la serie 0.x.

Método:

1. Revisar los `pub use` y los módulos públicos del crate.
2. Revisar el trait `Broker`, `IqOptionExtras`, `SyncBroker` y el registro.
3. Revisar los tipos de dominio afectados: payout, suscripciones, órdenes y
   eventos.
4. Revisar la superficie del binding Python.
5. Comparar con el plan 0.4.0 y clasificar cada cambio.

No se modificó código de producción.

### 3.5 Errores

| Tipo | Variantes actuales | Atributo | Implicación |
|---|---|---|---|
| `BrokerError` | 8: `Connection`, `Authentication`, `Timeout`, `NotConnected`, `Rejected`, `Domain`, `Transport`, `Internal` | Sin `#[non_exhaustive]` | Añadir una variante rompe matches exhaustivos |
| `DomainError` | 6: `AssetNotFound`, `MarketClosed`, `InsufficientBalance`, `InvalidAmount`, `OperationNotFound`, `StrikeUnavailable` | Sin `#[non_exhaustive]` | Añadir una variante rompe matches exhaustivos |

El plan de Fase 1 proponía errores explícitos para suscripción desconocida,
cotización no disponible, resultado de orden desconocido y conflicto de
idempotencia. Añadir variantes a estos enums **no es aditivo**. R34 se resuelve
sin tocarlos:

- `quote_payout` no usa error para indisponibilidad: devuelve
  `PayoutQuote { available: false, profit_percent: None, ... }`.
- `ManagedSubscriptions` usa `SubscriptionError`, un enum nuevo propiedad del
  trait de extensión.
- `ManagedOrders` usa `OrderError`, un enum nuevo propiedad del trait de
  extensión.
- Los adaptadores pueden envolver `BrokerError` dentro de esos errores nuevos;
  `BrokerError` y `DomainError` conservan sus 8 y 6 variantes.

`SubscriptionError` y `OrderError` son tipos nuevos, no variantes de los enums
existentes. Así no se rompe ningún `match` actual.

## 4. Contrato actual por bloque

### 4.1 Payout

Situación actual:

- El trait documenta `get_payout` como payout del catálogo y dice que
  `expiration_seconds` no altera la consulta.
- IQ Option cumple esa descripción: usa `asset.payout_percent`.
- Deriv no la cumple: consulta `proposal` con duración y `stake_referencia`.
- IQ Option usa `unwrap_or(0.0)` si no hay payout.
- Deriv convierte un `Rejected` en `closed: true` y `0.0`.
- `Payout` no distingue “sin dato” de “0%”.

Conclusión: el contrato común está **sobredocumentado** y no describe a Deriv.
La solución aprobada es conservar `get_payout` como API heredada y añadir
`quote_payout`/`PayoutQuote`, sin añadir campos a `Payout`.

### 4.2 Suscripciones

Situación actual:

- No hay `SubscriptionId`.
- No hay `unsubscribe`.
- IQ Option elimina el receptor local en `sub_velas.retain`, pero mantiene la
  entrada en `suscripciones` para replay.
- Deriv no elimina `sub_velas` ni `subs`.
- `subscribe_ticks` solo está implementado por Deriv; IQ emite `PriceTick` como
  efecto de `subscribe_candles`, pero la vía genérica devuelve un rechazo
  explícito de capacidad no soportada.
- IQ usa un canal de velas ilimitado; Deriv usa uno acotado de 128.
- El buffer de eventos es 1024 en IQ y 512 en Deriv.

Conclusión: no existe un ciclo de vida gestionado. La solución aprobada es un
trait de extensión con IDs, baja y replay solo de suscripciones activas.

### 4.3 Órdenes

Situación actual:

- `buy_binary`, `buy_digital_spot` y `buy_blitz` devuelven `OrderId` tras la
  respuesta del bróker.
- `abiertas` se inserta **después** de obtener el id.
- Si se envía y se pierde la respuesta, la orden puede existir en el bróker y
  no estar en `abiertas`.
- `get_operation_result` lee caché y devuelve `Pending` si no hay cierre.
- No hay id de operación del consumidor ni idempotencia.
- `OperationStatus` existe, pero no se expone una máquina de estados completa.
- `Unknown` no existe como estado de orden.

Conclusión: la ambigüedad es real. La solución aprobada es añadir
`ClientOrderId`, `OrderState`, `OrderView`, `get_order` y variantes de compra con
id de consumidor; no se cambia `OperationResult`.

### 4.4 Eventos

Situación actual:

- `Event` es `#[non_exhaustive]`.
- `EventsLost { count }` informa pérdida, no secuencia.
- `OrderOpened` y `OrderClosed` son los eventos de orden.
- `Disconnected`/`Reconnected` informan continuidad.
- No hay `OrderStateChanged`.
- Añadir una variante es compatible para consumidores que respetan
  `#[non_exhaustive]`; los matches internos deben cubrirla.

Conclusión: se puede añadir `OrderStateChanged` sin romper la firma del enum,
pero la documentación debe indicar que el consumidor necesita un brazo `_`.

## 6. Rupturas rechazadas para 0.4.0

No se aprueba ninguna de estas alternativas:

1. Cambiar `subscribe_candles` para devolver un handle en lugar de
   `CandleStream`. Rompe todos los consumidores actuales.
2. Cambiar `subscribe_ticks` para devolver `SubscriptionId`. Rompe la firma
   actual.
3. Añadir métodos obligatorios a `Broker`. Rompe implementadores externos.
4. Añadir campos a `Payout`, `Operation` o `Buy*Request`. Rompe literales de
   structs.
5. Reemplazar `get_payout` por `quote_payout`. Rompe consumidores y elimina la
   vía heredada.
6. Cambiar `OrderId` o `OperationResult`. Rompe el dominio y la serialización.
7. Reemplazar `Event` por un envelope con secuencia. Rompe matches y serialización.
8. Añadir variantes a `BrokerError` o `DomainError` sin declararlo C y sin
   migración. Rompe los matches exhaustivos actuales.

La vía aprobada es extensión aditiva y nuevos tipos.

## 7. Cambios de comportamiento que exigirán prueba y nota

Estos cambios no rompen la firma, pero no son “gratis”:

- **IQ `subscribe_ticks`:** antes rechazo explícito, ahora funciona. Hay que probar
  que no duplica ticks si además hay una suscripción de velas.
- **IQ `subscribe_candles` acotado:** un consumidor lento puede recibir un error
  o perder eventos de vela según la política. Debe documentarse.
- **Python `ticks()` en IQ:** antes lanzaba error; ahora devuelve ticks. Debe
  probarse contra el wheel.
- **`get_payout` documental:** el comportamiento de Deriv sigue siendo consulta
  por propuesta; no se debe presentar como catálogo.
- **`OrderStateChanged`:** el orden de eventos debe ser determinista y no debe
  duplicar `OrderOpened`/`OrderClosed`.
- **`Unknown`:** no se reintenta; la documentación debe ser explícita.

## 8. Decisiones de Fase 0

Quedan congeladas para la implementación:

1. `Broker` no cambia la firma de métodos existentes; los nuevos llevan
   implementación por defecto o viven en un trait de extensión.
2. Las capacidades nuevas van en traits de extensión cuando no puedan tener
   default.
3. `Payout` no se modifica; `PayoutQuote` es nuevo.
4. `get_payout` se conserva como heredado; `quote_payout` es la vía nueva.
5. `subscribe_candles` y `subscribe_ticks` se conservan; las variantes
   gestionadas son nuevas.
6. `OperationResult` no se modifica; `OrderState` es nuevo.
7. `Event::OrderStateChanged` se añade como variante nueva.
8. `SyncBroker` no se extiende a Deriv.
9. Python no recibe `AsyncClient` en 0.4.0.
10. No se implementan secuencias de eventos, benchmarks ni familias nuevas.
11. R34 se resuelve sin variantes nuevas: `quote_payout` usa `available: false`;
    `ManagedSubscriptions` usa `SubscriptionError`; `ManagedOrders` usa
    `OrderError`.

## 9. Riesgos abiertos

| Riesgo | Impacto | Mitigación |
|---|---|---|
| IQ no ofrece cotización por expiración para todas las modalidades | `quote_payout` devuelve `available: false` | Verificado 2026-11-09: digital por `price-splitter`; binaria/turbo/blitz sin canal de cotización. No inventar payout. |
| El bróker no confirma la baja de suscripción | El consumidor puede seguir recibiendo tráfico | Baja local, no afirmar baja del bróker sin evidencia |
| Una orden sin id no se puede correlacionar | `Unknown` puede quedar permanente | No reenviar; documentar; reconciliar solo si hay correlación |
| `ManagedSubscriptions` con `Box<dyn Broker>` | Object safety y acceso al trait | Extensión con `Broker` como supertrait y acceso explícito |
| Python comparte un `Mutex` sobre el bróker | Un handle de suscripción puede bloquear llamadas | Diseñar handle sin retener el lock durante el stream |
| `Event` nuevo rompe matches internos | Fallo de compilación | Actualizar matches y tests; consumidores externos usan `_` |
| `SyncBroker` no tiene paridad gestionada | Dos superficies divergen | Decidir si se añade wrapper aditivo o se documenta la exclusión |
| Nuevas variantes en `BrokerError`/`DomainError` | Evitado por R34 | Se usan `SubscriptionError`/`OrderError` y `available: false` |
| Tests Python no están en CI | El binding puede romperse sin señal | Incorporar `test_offline.py` al CI antes de release |

## 10. Criterios de salida de Fase 0

- Inventario de la superficie afectada completo.
- Matriz con todas las propuestas clasificadas A/B/C/D.
- Ninguna ruptura C en 0.4.0; R34 resuelta con errores propios.
- Decisiones de contrato registradas en el plan, incluida R34.
- Riesgos abiertos con mitigación.
- Sin cambios de código.

## 11. Estado

**Fase 0 completada en lo documental; matriz aprobada.** R34 se resolvió sin
tocar `BrokerError`/`DomainError`: cotización indisponible usa `available: false`;
suscripciones y órdenes gestionadas usan errores propios. La implementación no
ha comenzado. El siguiente paso es la Fase 1.
