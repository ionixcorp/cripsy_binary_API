# Plan de 0.4.0 — contratos, suscripciones y ciclo de órdenes

**Estado:** Fase 1 en curso: `PayoutQuote` y `quote_payout` implementados en Deriv e IQ; IQ cotiza digital por `price-splitter` y devuelve no disponible para binaria/blitz. Resto de Fase 1 pendiente.
**Base:** `cripsy_binary_API` 0.3.2 (0.3.1 + `PayoutQuote`/`quote_payout`), 89 tests Rust, binding Python sincrónico 0.3.1.
**Fase 0:** [`0.4.0-phase0-inventory.md`](0.4.0-phase0-inventory.md).
**Alcance:** Rust y Python.
**Objetivo:** cerrar las ambigüedades de contrato que hoy obligan al consumidor a
conocer diferencias internas entre IQ Option y Deriv, antes de añadir nuevas
capacidades de mercado.

## 1. Por qué 0.4.0

La auditoría de 0.3.1 encontró cuatro problemas que no son “falta de features”:

1. `get_payout` está documentado como payout de catálogo en el trait, pero
   Deriv consulta una propuesta por duración. El contrato común no describe lo
   que realmente hacen ambos adaptadores.
2. Las suscripciones no tienen identificador ni baja explícita. IQ Option
   retira el receptor local, pero mantiene la suscripción del bróker; Deriv no
   retira ni el registro de replay ni el canal de velas.
3. El ciclo de vida de una orden no distingue “enviada sin confirmación” de
   “rechazada”. Si se pierde la respuesta después de enviar, la orden puede
   existir en el bróker y no estar en `abiertas`.
4. La documentación promete más de lo que el contrato garantiza: “sin tokio”,
   “payout del catálogo” para ambos brókers, buffer único de 1024 y ticks
   genéricos en IQ Option.

La prioridad de 0.4.0 es que el consumidor pueda confiar en el contrato, no que
el README tenga más filas.

## 2. No objetivos de 0.4.0

Quedan explícitamente fuera de esta versión:

- Añadir Quotex u otro bróker.
- Añadir multiplicadores, acumuladores, dígitos o barreras.
- Extender `SyncBroker` a Deriv. Sigue siendo exclusivo de IQ Option.
- Implementar `asyncio` en Python. El binding sigue siendo sincrónico.
- Prometer benchmarks comparativos o superioridad de rendimiento.
- Añadir métricas, secuencias de eventos o recuperación histórica automática
  como bloques principales. Se dejan preparados los puntos de extensión, pero
  no se implementan en 0.4.0.

## 3. Principios de diseño

- **Contrato explícito:** cada método debe decir qué garantiza, qué no garantiza
  y qué ocurre si el bróker no lo soporta.
- **Compatibilidad primero:** las capacidades nuevas entran como traits de
  extensión o métodos con implementación por defecto; no se cambia el
  significado de un método existente en silencio.
- **Sin mocks:** las pruebas de bróker se hacen contra cuentas demo. Los tests
  offline solo validan mapeos y contratos.
- **Desconocido no es rechazado:** si no se puede saber el estado de una orden,
  el dominio debe representarlo como desconocido, no como error definitivo.
- **Sin estado global:** las suscripciones y órdenes viven en la sesión.
- **Semver y migración:** todo cambio incompatible se documenta en
  `CHANGELOG.md` y en una nota de migración.

## 4. Fases

### Fase 0 — Inventario y decisión de contrato (completada; R34 resuelto)

**Objetivo:** congelar las decisiones de API antes de escribir código.

Entregables:

- Tabla de contrato actual vs. contrato 0.4.0 para:
  - `get_payout` / cotización por expiración.
  - `subscribe_candles` / `subscribe_ticks` / baja.
  - `buy_*` / `get_operation_result` / estados.
  - `Event` y `OperationResult`.
- Decisión sobre extensión vs. cambio incompatible:
  - **Recomendado:** traits de extensión nuevos para lo que no pueda tener
    default; `quote_payout` se añade con implementación por defecto. No se
    rompen implementadores externos de `Broker`.
  - **Alternativa:** cambiar firmas en 0.4.0 y publicar migración. Solo si el
    consumidor acepta el coste.
- Decisión sobre `Payout` existente:
  - **Recomendado:** conservarlo como API heredada y añadir
    `PayoutQuote`/`quote_payout`; no reutilizar `Payout` para semánticas
    distintas.
- Decisión sobre órdenes sin id:
  - **Recomendado:** exponer `Unknown` y no reintentar automáticamente. Si el
    bróker no permite correlacionar, documentar la limitación.
- Decisión sobre errores: **R34 resuelto**. `BrokerError` y `DomainError` no
  cambian. `quote_payout` usa `available: false`; `ManagedSubscriptions` y
  `ManagedOrders` usan `SubscriptionError` y `OrderError`.

**Salida:** inventario completo y matriz aprobada. Sin código de producción.

### Fase 1 — Contratos de datos y compatibilidad

**Objetivo:** que los tipos públicos representen la realidad de ambos brókers.

Cambios propuestos:

1. **Payout**
   - Mantener `Payout` para el payout simple actual.
   - Añadir `PayoutQuote` con:
     - `symbol`
     - `option_type` (`OptionType`)
     - `expiration_seconds`
     - `profit_percent: Option<f64>`
     - `min_amount: Option<f64>`
     - `max_amount: Option<f64>`
     - `available: bool`
     - `captured_at: i64`
   - Añadir `quote_payout(symbol, option_type, expiration_seconds, amount)`
     como método con implementación por defecto que devuelve
     `PayoutQuote { available: false, profit_percent: None, ... }` cuando el
     bróker no ofrece cotización.
   - IQ Option: implementar con el canal de cotización que corresponda; si no
     hay dato, `available: false` y `profit_percent: None`. Nunca `0.0` como
     sustituto.
   - Deriv: implementar con `proposal`; un rechazo del bróker no debe
     convertirse en `closed: true` sin distinguir “mercado cerrado” de “parámetro
     inválido” o “límite”.
   - Mantener `get_payout` con su comportamiento actual, pero corregir su
     documentación por bróker y marcarlo como heredado.

2. **Suscripciones**
   - Añadir `SubscriptionId` opaco y `Clone`.
   - Añadir un trait de extensión `ManagedSubscriptions`:
     - `subscribe_candles_managed(req) -> Result<CandleSubscription, SubscriptionError>`
     - `subscribe_ticks_managed(symbol) -> Result<SubscriptionId, SubscriptionError>`
     - `unsubscribe(id) -> Result<(), SubscriptionError>`
   - `CandleSubscription { id, stream }`.
   - No cambiar `subscribe_candles` ni `subscribe_ticks` existentes en esta
     fase; se documentan como API no gestionada.

3. **Órdenes**
   - Añadir `ClientOrderId` (nuevo tipo, String).
   - Añadir `OrderState`:
     `Submitted`, `Accepted`, `Open`, `ResultPending`, `Closed`, `Rejected`,
     `Unknown`.
   - Añadir `OrderView` con id del bróker, id del consumidor, estado, resultado,
     timestamps y error de envío.
   - Añadir `Event::OrderStateChanged` (variante nueva; `Event` ya es
     `#[non_exhaustive]`).
   - Añadir el trait de extensión `ManagedOrders`:
     - `get_order(id) -> Result<OrderView, OrderError>`
     - `buy_binary_with_client_id(...) -> Result<OrderView, OrderError>`
     - `buy_digital_with_client_id(...) -> Result<OrderView, OrderError>`
     - `buy_blitz_with_client_id(...) -> Result<OrderView, OrderError>`
   - Mantener `OperationResult` para el resultado contable; no mezclarlo con el
     estado de la orden.

4. **Errores**
   - **R34 resuelto:** no se añaden variantes a `BrokerError` ni a `DomainError`.
   - `quote_payout` no devuelve error por indisponibilidad: devuelve
     `available: false` y campos opcionales en `None`.
   - `ManagedSubscriptions` usa `SubscriptionError` para suscripción
     desconocida, baja fallida y capacidad no soportada.
   - `ManagedOrders` usa `OrderError` para orden desconocida y conflicto de
     idempotencia.
   - Los errores de extensión pueden envolver `BrokerError`; no lo sustituyen.
   - No capturar y descartar errores para convertirlos en `Pending`.

**Criterios de salida:**

- Los tipos nuevos compilan con `async` y `blocking`.
- No hay cambios de firma en métodos existentes.
- Tests unitarios de serialización y estados.
- Documentación de cada campo nuevo.

### Verificación viva IQ (2026-11-09)

Se autenticó la cuenta demo por login HTTP + `ssid` y se observó el protocolo
real antes de implementar:

- `price-splitter.client-price-generated` entregó cotizaciones digitales reales.
  `quote_payout("USDZAR-OTC", OptionType::Digital, 60, 1.0)` devolvió
  `available: true`, `profit_percent: Some(120.27339981948155)`,
  `min_amount: Some(1.0)` y `max_amount: Some(20000.0)`.
- La misma llamada con `OptionType::Binary` devolvió `available: false` y
  `profit_percent: None`.
- `instrument-quotes-generated` no produjo frames para `digital-option`,
  `binary-option` ni `turbo-option` en las pruebas con 60/300 s. Por eso IQ
  solo cotiza digital; binaria/turbo/blitz quedan fuera de `quote_payout`.
- La cotización IQ es la del lado **CALL** (`call.bid` de la entrada `SPT`).
  `PayoutQuote` no tiene dirección; no se asume simetría con PUT.

Comando de la prueba: cargar `.env` con `scripts/iqoption/_env.ps1` y ejecutar
`cargo run --quiet --example estado_cuenta`.

### Fase 2 — Suscripciones con ciclo de vida

**Objetivo:** que suscribirse y desuscribirse sea explícito, observable y
repetible tras una reconexión.

Diseño:

- Cada suscripción tiene `SubscriptionId`, tipo, símbolo, intervalo, propietario
  lógico y contador de referencias.
- `unsubscribe`:
  1. marca la suscripción como cerrada localmente;
  2. elimina el emisor local;
  3. envía la baja al bróker cuando el protocolo la soporte;
  4. elimina el registro de replay;
  5. emite un evento de confirmación o de baja local, sin fingir confirmación del
     bróker.
- Si el bróker no tiene baja explícita:
  - se elimina el registro local y se deja de despachar;
  - se documenta que el bróker puede seguir enviando mensajes;
  - no se afirma “suscripción retirada en el bróker” si no se verificó.
- `subscribe_candles` de IQ Option deja de usar un canal ilimitado:
  - capacidad configurable;
  - política de consumidor lento explícita (`SlowConsumer` o descarte
    contabilizado);
  - no crecimiento de memoria sin límite.
- IQ Option implementa `subscribe_ticks` usando el stream de velas/precios que ya
  emite `PriceTick`, con un `SubscriptionId` propio.
- Deriv elimina `sub_velas` y `subs` al hacer `unsubscribe`; el replay solo
  incluye suscripciones con referencias activas.
- Python expone `unsubscribe` y usa la variante gestionada en `ticks()`.
- `close()` limpia todas las suscripciones de la sesión.

**Pruebas:**

- Abrir dos suscripciones al mismo símbolo, cerrar una y verificar que la otra
  sigue recibiendo.
- Cerrar todas y verificar que el registro de replay queda vacío.
- Reconectar y comprobar que no se reproduce una suscripción cerrada.
- Consumidor lento: verificar la política configurada y que no crece la memoria.
- IQ Option: `subscribe_ticks` entrega `PriceTick` y `unsubscribe` detiene el
  despacho local.
- Deriv: `unsubscribe` elimina el canal y el replay.
- Python: `ticks()` y `unsubscribe()` no dejan suscripciones residuales.

**Criterios de salida:**

- No hay suscripciones huérfanas en el registro de sesión.
- La reconexión no revive suscripciones cerradas.
- La prueba de consumidor lento no agota memoria.
- Documentación corregida: 1024 en IQ, 512 en Deriv y ausencia de baja explícita
  del bróker donde corresponda.

### Fase 3 — Ciclo de vida de órdenes

**Objetivo:** distinguir solicitud, aceptación, apertura, resultado pendiente,
cierre, rechazo y estado desconocido.

Diseño:

- `ClientOrderId` generado por el consumidor.
- `buy_binary`, `buy_digital` y `buy_blitz` aceptan la variante con id de
  consumidor, sin eliminar las firmas actuales.
- Antes de enviar:
  - registrar `Submitted` con `ClientOrderId`;
  - no registrar `Open` todavía.
- Al recibir id del bróker:
  - `Accepted` y luego `Open`;
  - asociar `ClientOrderId` ↔ id del bróker.
- Al recibir cierre:
  - `Closed` + `OperationResult`;
  - una sola transición, idempotente.
- Si vence el timeout después de enviar:
  - `Unknown`, no `Rejected`;
  - no reenviar automáticamente;
  - intentar reconciliación por historial o por id de consumidor si el bróker lo
    permite;
  - si no se puede correlacionar, dejar `Unknown` y documentarlo.
- `get_operation_result` sigue leyendo caché, pero `get_order` devuelve
  `OrderView` con el estado completo.
- `wait_result` sigue esperando el cierre, con timeout explícito.
- Idempotencia:
  - el mismo `ClientOrderId` no genera una segunda orden;
  - si el bróker no ofrece idempotencia nativa, la garantía es local y se
    documenta como tal.

**Pruebas:**

- Compra exitosa: `Submitted` → `Accepted` → `Open` → `Closed`.
- Timeout después de enviar: `Unknown`, sin `Rejected` y sin reenvío.
- Cierre tardío tras `Unknown`: `Closed` una sola vez.
- Doble `ClientOrderId`: segunda llamada rechazada como conflicto.
- Desconexión antes de la confirmación: no se pierde el estado `Unknown`.
- Reconexión: una orden aceptada se reconcilia; una no confirmada no se inventa.
- IQ Option y Deriv: mismos estados de dominio, distinta fuente de reconciliación.

**Criterios de salida:**

- No hay orden aceptada sin estado `Open`.
- No hay orden enviada sin estado `Submitted` o `Unknown`.
- No se emite `OrderClosed` dos veces.
- La documentación explica qué garantiza cada bróker y qué no.

**Verificación viva, cuenta demo:**

  de `unsubscribe`; reconectar y verificar replay solo de activas.
- Deriv: mismo ciclo para velas y ticks; comprobar que `subs` no reproduce una

## 6. Riesgos y mitigaciones

| Riesgo | Mitigación |
|---|---|
| IQ Option no confirma baja de suscripción | No prometer baja del bróker; medir despacho local y documentar |
| Deriv no permite correlacionar una orden sin `contract_id` | Estado `Unknown` explícito; no reenviar; reconciliar por historial si es posible |
| Añadir métodos al trait rompe implementadores externos | Traits de extensión o métodos con implementación por defecto |
| `Event` nuevo rompe matches exhaustivos | Ya es `#[non_exhaustive]`; aun así, documentar la variante nueva |
| Cambiar `Payout` rompe consumidores | Mantener `Payout` y añadir `PayoutQuote` |
| El canal de velas de IQ crece sin control | Canal acotado y política de consumidor lento |
| Python no tiene paridad con Rust | Tests de contrato y mismos escenarios de dominio |
| Pruebas vivas dependen de cuenta demo | Registrar credenciales fuera del repo; marcar pruebas como live y no ejecutarlas en CI |

## 7. Decisiones de contrato

Registradas el 2026-11-09. Las decisiones 1-6 están aprobadas; la 3 es
aprobación condicionada. La aprobación no inicia la implementación ni autoriza
publicación.

| # | Decisión | Resolución | Condición |
|---|---|---|---|
| 1 | Extensión vs. ruptura | **Aprobado: extensión** | `Broker` conserva la firma de sus métodos existentes; `quote_payout` se añade con default y el resto de capacidades nuevas va en traits de extensión. No se añaden métodos obligatorios a `Broker`. |
| 2 | Payout | **Aprobado: mantener y añadir** | `get_payout` queda como API heredada, con documentación por bróker; `quote_payout` es la vía nueva. `PayoutQuote` usa `Option`/`available`; no se fabrica `0.0`. Deriv no convierte cualquier rechazo en `closed: true`. |
| 3 | Orden desconocida | **Aprobado con condición** | Se expone `Unknown`; no se reenvía automáticamente. Solo se reconcilia si hay id del bróker o correlación verificable. Si no se puede, se documenta y se deja `Unknown`; nunca se emite un cierre inventado. |
| 4 | Secuencias de eventos | **Aprobado: fuera de 0.4.0** | 0.4.0 mantiene `EventsLost { count }` y no promete recuperación exacta. No se añade una API de secuencias; el diseño queda para 0.5.0. |
| 5 | Python async | **Aprobado: fuera de 0.4.0** | El `Client` sincrónico se conserva. 0.4.0 solo añade paridad de contratos y suscripciones gestionadas; `AsyncClient` queda para otra versión. |
| 6 | Errores explícitos | **Aprobado: R34 resuelto** | `BrokerError` y `DomainError` quedan intactos. `quote_payout` usa `available: false`; `ManagedSubscriptions` usa `SubscriptionError`; `ManagedOrders` usa `OrderError`. |

## 8. Definición de terminado

0.4.0 se considera terminada cuando:

- El contrato de payout distingue catálogo, cotización y dato no disponible.
- Las suscripciones tienen id, baja y limpieza; la reconexión no revive las
  cerradas.
- Las órdenes tienen estados explícitos y `Unknown` no se confunde con rechazo.
- IQ Option y Deriv tienen garantías documentadas por separado.
- Los tests Rust y Python pasan; las pruebas vivas tienen evidencia.
- `CHANGELOG` y migración están escritos.
- No se añadió ninguna funcionalidad fuera de alcance para “aprovechar” la
  versión.
