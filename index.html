Qué es cripsy_binary_API

Qué es cripsy_binary_API

cripsy_binary_API es una API moderna, en Rust, para operar contra brókers de

opciones binarias. Diseñada desde cero, con estas propiedades:

  • Núcleo asíncrono: el adaptador es async/await nativo.
  • Fachada sincrónica: broker::sync::SyncBroker permite consumir la misma

API con llamadas bloqueantes, sin tokio ni await.

  • Sin estado global estático y sin polling: cada petición crea un canal y la

respuesta se correlaciona por request_id; los resultados de las órdenes

llegan por eventos.

  • Multibróker: una interfaz común (Broker) con adaptadores por bróker;

el primero es IQ Option.

  • Streams nativos de alta densidad: ~3 ticks de precio por segundo por

activo en la medición documentada; hasta 75 activos por sesión sin rechazos.

  • Tipado de extremo a extremo: nada de diccionarios crudos en la frontera

pública.

Qué no hace

  • No calcula indicadores: entrega los que el bróker publique, o nada si el

bróker no los soporta. Puedes calcular los tuyos con el histórico y el stream.

  • No es una interfaz gráfica ni un bot: es una librería para que tú

construyas encima.

  • No gestiona tu dinero: envía órdenes al bróker cuando se lo pides.

Requisitos

  • Rust 1.86 o superior (rustup).
  • Credenciales del bróker (se recomienda cuenta demo para empezar).
  • Windows, Linux o macOS.

Limitaciones conocidas

  • Reconexión automática (0.2.0): si el WebSocket cae, la sesión

reautentica, restaura perfil, catálogo y suscripciones, y lo informa con

Event::Disconnected y Event::Reconnected { intentos, downtime_ms }.

Mientras no hay socket, las llamadas devuelven BrokerError::NotConnected.

  • Órdenes en vuelo: se descartan con error y no se reenvían al reconectar;

reenviarlas significaría operar con un mercado distinto al decidido.

  • Huecos de stream: la reproducción restablece las suscripciones, pero los

datos ocurridos durante la caída se recuperan con el histórico, no por el

stream.

  • Resultado de operación desde caché: get_operation_result lee la caché

alimentada por eventos; no consulta al bróker. Sin el stream activo, una orden

puede quedarse en Pending.

  • Payout del catálogo: get_payout devuelve el payout publicado para el

activo; el parámetro de expiración no cambia la consulta. Los cambios en vivo

llegan por Event::PayoutChanged.

  • Suscripciones sin baja explícita: al soltar el CandleStream la

suscripción se retira en el siguiente despacho de velas.

  • Pérdida de eventos: si el consumidor se atrasa más que el buffer (1024),

el stream entrega Event::EventsLost { count } y continúa.

  • Indicadores técnicos: dependen de lo que el bróker publique para cada

activo; hoy los rechaza para los activos probados.

Sesión y cuentas

Sesión y cuentas

Conectar

La conexión combina un login HTTP y un WebSocket:

  1. POST https://auth.iqoption.com/api/v2/login con {identifier, password}.

La respuesta trae la cookie ssid (también en el cuerpo).

  1. Se abre wss://iqoption.com/echo/websocket y se envía

{"name":"ssid","msg":"<SSID>"} como primer mensaje.

  1. El bróker responde con profile, que incluye los balances y el

balance_id activo.

La sesión queda operativa cuando el catálogo de activos se ha recibido

(get-initialization-data v3.0).

Cuentas: demo y real

El perfil contiene varias cuentas. El tipo se identifica por balance.type:

typeCuenta
1Real
4Demo (practica)
otrostratados como real

Al conectar puedes elegir la cuenta con AccountSelection:

let config = IqOptionConfig {
    email: std::env::var("IQOPTION_EMAIL")?,
    password: std::env::var("IQOPTION_PASSWORD")?,
    account: AccountSelection::Practice,  // demo explícita
    ..IqOptionConfig::default()
};

let broker = IqOptionBroker::nuevo(BrokerParams::IqOption(config)).await?;

Consultas disponibles

Todas son async y devuelven Result<_, BrokerError>:

LlamadaQué devuelve
session().await?Copia de la sesión activa (balance_id, tipo de cuenta, offset de hora)

Nota sobre el catálogo: el bróker publica el mismo símbolo en hasta tres grupos

(binary, turbo y blitz) con metadatos distintos entre ellos. El catálogo

contiene una entrada por grupo; para operar blitz usa la de

AssetClass::Blitz (ver la sección 06).

Notas importantes

  • Toda orden lleva user_balance_id: sin cuenta activa el bróker la rechaza.
  • La expiración se calcula con la hora del servidor (timeSync), no con el

reloj local.

  • Las cuentas demo tienen saldo independiente; las operaciones de prueba se ven

solo cuando la demo es la cuenta activa.

Eventos de comisiones y operaciones de terceros

Dos canales más, ambos con suscripción explícita (los eventos salen por

broker.events()):

// Comisiones por tipo de instrumento (binary-option, turbo-option, digital-option)
broker.subscribe_commission_changes().await?;
while let Some(ev) = broker.events().await?.next().await {
    if let Event::CommissionChanged(c) = ev {
        // c.symbol, c.instrument_type, c.commission_value
    }
}

// Operaciones de terceros (live-deal) para un activo concreto
broker.subscribe_live_deals("EURUSD-OTC").await?;
while let Some(ev) = broker.events().await?.next().await {
    if let Event::LiveDeal(deal) = ev {
        // deal.symbol, deal.direction, deal.amount, deal.created_at
    }
}
  • commission-changed emite Event::CommissionChanged con la comisión en

puntos (payout = 100 − comisión).

  • live-deal / live-deal-binary-option-placed emiten Event::LiveDeal

(operaciones de otros usuarios: señal de flujo del mercado).

  • El volumen depende de la actividad del bróker: en horarios tranquilos puede

no llegar nada (verificado en vivo: suscripción aceptada, 0 eventos en

ventana de fin de semana).

Históricos: límites verificados

Históricos: límites verificados

Los datos históricos se piden con get_candles(...). Los límites están

verificados en vivo contra el bróker (2026-10-27):

Tamaño de velaProfundidad máxima
1 segundo7 días exactos (a 14 días: 0 velas)
1 minutoentre 45 y 90 días
5 minutosentre 270 y 330 días
15 min, 1 h, 4 h, 1 díamás de 2 años

Reglas prácticas:

  • count máximo por petición: 1000 velas (pedir más devuelve 1000).
  • to debe ser el inicio de una vela ya cerrada. Usa el ayudante

broker::historico::ultimo_cierre(ahora, intervalo), que resta un paso al

múltiplo del intervalo; con to dentro de la vela en curso la respuesta llega

vacía.

  • Los datos son contiguos: sin huecos dentro de la ventana disponible.

Tamaños disponibles: 1, 5, 15, 30, 60, 300, 900, 3600, 14400 y 86400 s.

Descargar toda la semana en velas de 1 s

Iterando end_time hacia atrás, count × interval segundos por petición:

let mut fin = None;
loop {
    let velas = broker.get_candles(CandleRequest {
        symbol: "USDZAR-OTC".into(),
        interval: 1,
        count: 1000,
        end_time: fin,
    }).await?;
    if velas.is_empty() { break; }
    fin = Some(velas.last().unwrap().from);
    // ~605 peticiones cubren los 7 días completos de este activo
}

El protocolo también permite paginar por id (to_id), pero nuestra API aún

no lo expone: la descarga se hace iterando end_time hacia atrás.

Nota sobre densidad en histórico

El histórico es de velas: no existe densidad de tick en el pasado. La

granularidad fina máxima es la vela de 1 segundo. Para densidad intrasegundo

hay que usar el stream en vivo (ver la próxima página).

Stream en vivo: velas multi-tamaño y ticks

Stream en vivo: velas multi-tamaño y ticks

Dos mecanismos nativos, sin polling:

1. Velas en vivo (subscribe_candles)

Una única suscripción entrega todos los tamaños de vela de un activo

(1 s, 5 s, 1 m, 5 m, ... hasta diario). El adaptador filtra por el tamaño

pedido: interval = 0 significa "todos los tamaños".

let mut stream = broker.subscribe_candles(CandleSubscribe {
    symbol: "USDZAR-OTC".into(),
    interval: 60,           // velas de 1 minuto
}).await?;

while let Some(vela) = stream.next().await {
    let vela = vela?;       // Candle { from, to, open, close, high, low, volume }
    // estrategia...
}

2. Ticks de precio (Event::PriceTick)

Cada mensaje del stream trae el precio spot (value, bid, ask) con marca

temporal en nanosegundos. La sesión lo emite como evento:

let mut eventos = broker.events().await?;
while let Some(ev) = eventos.next().await {
    if let Event::PriceTick { symbol, tick } = ev {
        // tick.price, tick.bid, tick.ask, tick.at_ms
    }
}

El bus de eventos tiene buffer acotado (1024 eventos). Si tu consumidor se

atrasa más que el buffer, se descartan los eventos intermedios y el stream

entrega Event::EventsLost { count } con la cuenta de los perdidos; el stream

sigue abierto. Consume sin bloqueos largos entre lectura y lectura.

Medido en vivo (2026-10-27, varios mercados OTC):

Activo (mercado)Mensajes/sCambios de precio/s
XAUUSD-OTC (materia prima)3.673.20
ETHUSD-OTC (cripto)3.402.80
EURUSD-OTC (forex)3.202.67

Hallazgos clave:

  • La densidad (~3/s por activo) no depende de suscribir multi-tamaño o un

tamaño específico: da igual.

  • Caudal proporcional al número de activos: con 20 activos suscritos se

midieron 61 mensajes/s (3.07 por activo).

  • Escala verificada hasta 75 activos en una sola sesión: 0 rechazos,
  1. No se probó por encima de esa

cifra, así que no se documenta un techo.

  • La densidad exacta depende de la liquidez y el horario del activo; los

ejemplos miden mercados OTC de fin de semana.

Sin sondeo

Cada mensaje del WebSocket se procesa al instante y se emite como evento: no

hay bucles de consulta ni latencia artificial añadida. La densidad que mides es

la que el bróker publica.

Fachada sincrónica e histórico

Fachada sincrónica e histórico

La API ofrece el mismo núcleo de dos formas. Si tu proyecto no es async, usa la

fachada bloqueante: no necesitas tokio ni await.

Fachada sincrona

use cripsy_binary_api::broker::config::{AccountSelection, BrokerParams, IqOptionConfig};
use cripsy_binary_api::broker::sync::SyncBroker;

fn main() -> Result<(), Box<dyn std::error::Error>> {
    let cfg = IqOptionConfig {
        email: std::env::var("IQOPTION_EMAIL")?,
        password: std::env::var("IQOPTION_PASSWORD")?,
        account: AccountSelection::Practice,
        ..IqOptionConfig::default()
    };

    let mut broker = SyncBroker::connect(BrokerParams::IqOption(cfg))?;

    // Todo bloqueante, misma semántica que la versión async.
    let balance = broker.get_balance()?;
    println!("balance: {} {}", balance.amount, balance.currency);

    let activos = broker.list_assets()?;
    let abierto = activos
        .iter()
        .find(|a| a.symbol.ends_with("-OTC") && a.status == cripsy_binary_api::domain::MarketStatus::Open)
        .expect("OTC abierto");

    // Streams como iteradores bloqueantes.
    let mut velas = broker.subscribe_candles(cripsy_binary_api::domain::CandleSubscribe {
        symbol: abierto.symbol.clone(),
        interval: 60,
    })?;
    if let Some(v) = velas.next() {
        println!("vela en vivo: {:?}", v?);
    }

    let mut eventos = broker.events()?;
    for ev in eventos.take(5) {
        println!("evento: {ev:?}");
    }

    broker.disconnect()?;
    Ok(())
}

Reglas:

  • No uses la fachada dentro de un contexto async: bloquearía el executor

del llamador. En async, usa el trait Broker directamente.

  • Los iteradores tienen timeout de 30 s: si no llega nada en ese plazo, el

iterador se cierra (vuelve a suscribirte si lo necesitas).

  • El bus de eventos tiene buffer acotado: un consumidor lento puede perder

eventos, igual que en async.

Métodos disponibles (todos bloqueantes): session, is_connected,

disconnect, get_balance, get_account_type, switch_account,

list_assets, asset_status, get_candles, subscribe_candles,

get_position_history, get_payout, get_asset_profile,

get_technical_indicators, subscribe_live_deals,

subscribe_commission_changes, events, buy_binary,

buy_digital_spot, sell_option, get_operation_result.

Ayudante de histórico

cripsy_binary_api::broker::historico facilita descargar el histórico granular

(límites verificados: 1 s × 7 días, 1000 velas por página):

Ejemplo:

use cripsy_binary_api::broker::historico::{descargar, paginas_estimadas};

// Antes de descargar, sabe cuánto costará:
let paginas = paginas_estimadas(1, desde_epoch, hasta_epoch);

// Descarga completa con paginación (devuelve una Ventana con las velas).
let ventana = descargar(
    &broker,               // &dyn Broker (async)
    "USDZAR-OTC",
    1,                     // intervalo: 1 segundo
    desde_epoch,           // epoch segundos
    hasta_epoch,           // epoch segundos
).await?;

println!("{} velas en {} páginas", ventana.velas.len(), ventana.paginas);

Con size=1 y el límite de 7 días del bróker, una semana completa de un activo

son ~605 páginas de 1000.

Opciones digitales

Opciones digitales

Las digitales usan el protocolo v2: la compra se arma con el instrumento

que publica el stream de precios del bróker.

Flujo

  1. Suscribirse a price-splitter.client-price-generated (el adaptador lo hace

solo al comprar).

  1. Esperar el mensaje del periodo deseado y tomar la entrada spot

(strike == "SPT"): de ahí salen call.symbol o put.symbol (el

instrument_id) y el instrument_index.

  1. Enviar digital-options.place-digital-option v2.0 con:
{
  "user_balance_id": <id_de_tu_perfil>,
  "instrument_id": "do1380A20261027D002400T1MCSPT",
  "asset_id": 1380,
  "instrument_index": 4046465,
  "amount": "1.0"
}

Detalles que el bróker exige (verificados en vivo):

  • amount viaja como texto ("1.0"); como número responde

INVALID_SCHEMA.

  • El instrument_index debe salir del mismo mensaje de precio que el

instrumento: los índices rotan.

  • Si el instrumento elegido no es el spot, el bróker responde

bad quote (status 4008).

Llamada

let orden = broker.buy_digital_spot(BuyDigitalRequest {
    symbol: "USDZAR-OTC".into(),
    amount: 1.0,
    direction: Direction::Call,
    duration_minutes: 1,
    strike: 0.0,   // lo elige el price-splitter
}).await?;

Resultado

Las digitales cierran por el canal de cartera position-changed, no por

option-closed como el resto. El adaptador correlaciona la orden por

instrument_id y emite Event::OrderClosed igual que las demás, así que el

consumidor no ve la diferencia:

if let Event::OrderClosed { id, result } = /* ... */ {
    // result: Win(neto) | Loss(monto) | Equal(monto) | Pending
}

El resultado también queda en el cache: get_operation_result(&id) devuelve

el mismo valor sin consultar al bróker (sin polling).

Semántica de montos

  • close_profit / win_amount son el crédito total (inversión +

ganancia), no la ganancia.

  • El adaptador ya devuelve la ganancia neta (crédito − inversión).
  • En socket-option-closed el campo amount viene en micro-unidades

(1 000 000 = 1 USD); sum es la inversión legible.

Opciones clásicas (turbo / binary)

Opciones clásicas (turbo / binary)

Las clásicas usan el mensaje binary-options.open-option v1.0. La

clasificación la hace la duración, igual que la plataforma:

  • ≤ 5 minutos → turbo (option_type_id 3).
  • > 5 minutos → binary (option_type_id 1).

La expiración se calcula con la tabla de minutos/cuartos de hora del bróker:

la API reproduce la lógica verificada (candidatos de minuto para turbo, de

cuarto de hora con 5 minutos de margen para binary) y elige el más cercano a

la duración pedida.

Llamada

let orden = broker.buy_binary(BuyBinaryRequest {
    symbol: "USDZAR-OTC".into(),
    amount: 1.0,
    direction: Direction::Put,
    expiration_minutes: 1,
    option_type: OptionType::Binary,
}).await?;

El bróker confirma con buyComplete; la orden queda identificada por

OrderId.

Ciclo de vida por eventos

El resultado llega por eventos, no por polling:

  1. option-opened — apertura tipada (option_type, option_type_id, montos).
  2. option-closed — resultado final con result (win/loose/equal) y montos.
  3. socket-option-closed — evento equivalente con el detalle micro-unitario.
let mut eventos = broker.events().await?;
while let Some(ev) = eventos.next().await {
    if let Event::OrderClosed { id, result } = ev {
        println!("orden {id}: {result:?}");
    }
}

get_operation_result(&id) consulta el cache alimentado por esos eventos

(siempre disponible, sin latencia de red).

Validaciones antes de enviar

  • El activo debe estar en estado Open; si no, error MarketClosed.
  • Se valida el monto mínimo del catálogo (min_amount) cuando el bróker lo

publica; el máximo lo aplica el bróker (responde con su mensaje de rechazo).

  • En blitz se valida además que la duración esté entre las admitidas por el

grupo blitz (expiration_times ∪ rollovers).

Opciones blitz

Opciones blitz

Blitz es el tipo más nuevo del protocolo (option_type_id 12, mensaje

binary-options.open-option v2.0) y tiene sus propias reglas. Los errores

de implementación típicos se documentan aquí porque el bróker los reporta con

mensajes engañosos.

Reglas verificadas

  1. El grupo blitz tiene metadatos propios. El mismo símbolo aparece en

binary, turbo y blitz con duraciones distintas (binary declara

[900]; blitz [30, 45, 60, 120, 180, 300], y los rollovers añaden

  1. Resuelve el activo contra el grupo blitz (AssetClass::Blitz),

nunca contra binary.

  1. expired debe ir alineado al múltiplo de la duración:

(ahora_servidor / duracion + 1) * duracion. Un expired desalineado

recibe active is suspended — que parece un estado del mercado pero es un

error de forma.

  1. profit_percent va como entero (el bróker rechaza "86.0").

Llamada

let orden = broker.buy_binary(BuyBinaryRequest {
    symbol: "USDZAR-OTC".into(),
    amount: 1.0,
    direction: Direction::Call,
    expiration_minutes: 30,        // para blitz: SEGUNDOS (ver nota)
    option_type: OptionType::Blitz,
}).await?;

Nota de nomenclatura: en BuyBinaryRequest, el campo expiration_minutes

transporta segundos cuando option_type es Blitz (las duraciones del

catálogo blitz están en segundos).

Rollovers

La respuesta de apertura del bróker trae rollover_params (deadtime,

limit, offset, offset_from_expiration, amount_multiplier): son los

parámetros de renovación automática que el bróker aplica a la orden. Hoy

buy_binary devuelve solo el OrderId; los parámetros de rollover viajan en

la respuesta del bróker pero no se exponen aún en la API pública.

Estado actual

Blitz está verificado de extremo a extremo en cuenta demo: apertura

(status 2000, type: "blitz", respuesta con rollover_params) y cierre por

evento con resultado y delta de balance coincidente.

El bróker puede reportar active is suspended / `asset is not available at the

moment` para activos concretos: es un estado por activo que el bróker

decide (OTC blitz opera 24/7, no es cierre de mercado). Si recibes ese error,

prueba otro activo o más tarde; el mensaje de error es literalmente el del

bróker.

Si una compra blitz se rechaza, revisa antes tu petición: las causas

confirmadas fueron duración no admitida por el grupo blitz y expired

desalineado (arriba), no el estado del mercado.

Herramientas del proyecto

Herramientas del proyecto

Todo lo necesario para instalar, verificar y desarrollar está en tres lugares:

  • installation/ — instalación guiada y verificación del entorno.
  • scripts/ — compuerta de calidad, generación de la documentación y scripts

listos para usar contra el bróker.

  • examples/ — uso real de la API (lectura, consumo sincrónico y una orden demo).

.\installation\install.ps1

El instalador, pidiendo tu aprobación en cada paso:

  1. Verifica el entorno (check_env.ps1): Rust, cargo, git y .env.
  2. Si falta una herramienta, ofrece instalarla (rustup por winget o descarga

oficial) — solo si apruebas.

  1. Compila la librería en modo release, en sus dos variantes (async y blocking).
  2. Crea .env a partir de .env.example para tus credenciales.
  3. Genera la documentación navegable y, si lo apruebas, ejecuta

Indicadores técnicos del bróker

Indicadores técnicos del bróker

La respuesta corta

El bróker sí tiene un canal de indicadores técnicos, pero hoy rechaza todos

los activos. Nuestra API lo implementa igual: cuando el bróker lo habilite,

funciona sin cambios.

Qué se verificó

El canal existe y responde con mensajes tipados:

  • Petición: sendMessage con trading-signals.get-technical-indicators

v1.0 y body {"id": <active_id>}.

  • Respuesta: mensaje technical-indicators con msg.indicators (forma libre

del bróker) o msg.message de error.

Errores observados en la validación (2026-10-27):

PruebaRespuesta del bróker
Varias docenas de activos (OTC y no-OTC, abiertos y cerrados)Active is not supported: active id 'X' (status 4150)
id como textoINVALID_SCHEMA (debe ser entero)
versión 2.0sin respuesta

Es decir: el canal está vivo pero el servicio no entrega indicadores a esta

cuenta/estado actual. No es un problema de formato.

Cómo usarlo cuando esté disponible

let indicadores = broker.get_technical_indicators("EURUSD-OTC").await?;
// indicadores.indicators trae la forma libre del bróker

La API es de transporte: no calcula ni configura indicadores, entrega lo

que el bróker publique. Si el bróker no soporta el activo, recibes

BrokerError::Rejected con el mensaje textual del bróker.

Alternativa: calcular los tuyos

Si prefieres no depender del canal, puedes calcular indicadores a partir de:

  • Histórico: hasta 1s × 7 días por activo (ideal para backtests densos).
  • Stream en vivo: ~3 ticks/s por activo para tiempo real.
  • Mood y popularidad: Event::TradersMoodChanged y

Event::TopAssetUpdated vienen del bróker como señales adicionales.

Con velas de 1 segundo reconstruidas desde el histórico puedes alimentar

cualquier indicador (medias, RSI, bandas, pivotes) con resolución de un segundo.

Reconexión de sesión

Reconexión de sesión

Desde la versión 0.2.0 la sesión no se queda caída cuando el WebSocket se

interrumpe: una tarea supervisora la restablece y el consumidor recibe el aviso

por el mismo stream de eventos que ya usa.

Qué ocurre cuando cae la conexión

  1. El bucle de despacho termina y se descartan las peticiones en vuelo

(fail_all), de modo que ninguna espera queda colgada hasta su timeout.

  1. Se emite Event::Disconnected { motivo } con el motivo observado: error de

lectura, error de escritura o cierre por parte del bróker.

  1. La sesión vuelve a autenticarse con las credenciales de la configuración y

abre un WebSocket nuevo con reintentos y backoff exponencial

(backoff_base_ms … backoff_max_ms).

  1. Con el socket nuevo se rehace el handshake: ssid → perfil (sesión y

balances) y datos de inicialización (catálogo de activos).

  1. Se reproduce el registro de suscripciones completo.
  2. Se emite Event::Reconnected { intentos, downtime_ms } y el despacho

continúa.

Los streams de velas entregados antes de la caída siguen siendo válidos: no

se cierran y vuelven a recibir datos cuando la suscripción se reproduce.

Peticiones durante la caída

Mientras no hay socket, solicitar y las suscripciones devuelven

BrokerError::NotConnected de inmediato. No se encola nada a propósito: una

orden guardada para más tarde se ejecutaría contra un mercado distinto del que

motivó la decisión, que en opciones binarias con expiración corta cambia el

resultado por completo.

La cola de salida está acotada (TransportConfig::cola_salida, 256 por

defecto). Si el productor supera esa capacidad sin que el socket consuma, la

llamada espera en lugar de crecer en memoria sin límite.

Credenciales rechazadas

Un fallo de autenticación es terminal: la reconexión se abandona y la sesión

queda cerrada. Reintentar el login en bucle es la forma más rápida de que el

bróker bloquee la cuenta, así que el supervisor no lo hace. Los fallos de red o

de handshake sí se reintentan.

Personalización

use cripsy_binary_api::broker::config::{IqOptionConfig, TransportConfig};

let cfg = IqOptionConfig {
    transport: TransportConfig {
        backoff_base_ms: 250,   // primera espera
        backoff_max_ms: 8_000,  // techo
        cola_salida: 256,       // capacidad de la cola de salida
        ..TransportConfig::default()
    },
    ..IqOptionConfig::default()
};

Reconciliación de cierres

Una orden se abre y se registra como pendiente. Si su cierre ocurre durante la

caída, el evento nunca llega; al reconectar la sesión consulta el historial de

posiciones del balance activo y recupera esos cierres:

  • Solo se completan identificadores que esta sesión abrió y siguen pendientes.

Un cierre ajeno no aparece en la caché del consumidor.

  • El resultado se publica como Event::OrderClosed, igual que un cierre

normal, así que el consumidor no necesita una ruta distinta.

  • Win lleva la ganancia neta, Loss el importe perdido y Equal el importe

devuelto, calculados desde el PnL de la posición.

La consulta es paginada (100 posiciones por página, hasta 10 páginas) y se

detiene en cuanto encuentra todos los cierres pendientes: una sesión caída

durante horas no bloquea el despacho recorriendo el historial completo.

Si el historial no responde, la reconexión continúa y se registra el aviso en

tracing; las órdenes afectadas quedan como estaban.

Qué no resuelve

  • Órdenes en vuelo: se descartan con error y no se reenvían. Una orden

aceptada por el bróker sí se reconcilia al volver.

  • Huecos de datos: las velas y ticks ocurridos durante la caída no llegan

por el stream; se recuperan con get_candles o la descarga paginada.

  • Cierres fuera de la ventana del historial: la reconciliación recorre

hasta 10 páginas de 100 posiciones y se detiene al encontrar lo que busca o

al recibir una página incompleta. Un cierre más antiguo exige consultar el

historial con get_position_history.

Observabilidad

Los avisos de reconexión se registran con tracing (warn al perder el

socket, info al restablecerlo, error si se abandona). El consumidor que

quiera métricas propias puede contar Disconnected frente a Reconnected y

usar downtime_ms para medir la indisponibilidad real.

Estado verificado

La suite viva fuerza la caída del socket y comprueba el ciclo completo:

Disconnected, reconexión, operativa posterior y replay de una suscripción.

Última ejecución: 1 intento de reconexión, 4.938 ms sin conexión y vela

El recorrido multi-página tiene prueba con historiales simulados: localiza
